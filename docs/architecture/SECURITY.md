# 보안 설계

## 1. 보호 대상

- JWT 서명 키
- Google ID 토큰
- 액세스 토큰과 리프레시 토큰 원문
- 리프레시 토큰 해시와 패밀리 관계
- 사용자 외부 제공자 식별자
- 재화, 캐릭터, 스테이지 보상, 방 구성 데이터
- SQLite DB와 백업 파일

## 2. 인증 경계

- Bearer JWT는 HTTP 계층에서 검증하고 `CallerProto`로 정규화합니다.
- Handler는 `ClaimsPrincipal`과 HTTP 객체를 직접 읽지 않습니다.
- `sub`는 내부 사용자 ID로 파싱하고 사용자 존재 여부를 업무 계층에서 확인합니다.
- 발급자, 대상, 수명, 서명 키를 모두 검증합니다.
- 기본 액세스 토큰 수명은 60분, 허용 시계 오차는 30초입니다.
- 배치의 모든 요소는 동일한 호출자 문맥을 공유합니다.

## 3. Google 로그인

- Google ID 토큰은 허용된 Client ID 목록을 audience로 검증합니다.
- 토큰의 subject가 비어 있으면 거부합니다.
- 이메일과 표시 이름은 현재 계정 식별 기준으로 사용하지 않습니다.
- provider와 providerUserId 조합의 DB 유일 제약을 신뢰 경계의 마지막 방어선으로 둡니다.
- 초기 사용자명 생성 시 subject 원문을 저장하거나 노출하지 않습니다. SHA-256 파생값의 충분한 길이를 사용하고 사용자명 유일 충돌을 처리합니다.

## 4. 리프레시 토큰

- CSPRNG로 32바이트 이상 생성하고 Base64Url로 표현합니다.
- DB에는 SHA-256 해시만 저장합니다.
- 토큰 비교와 조회는 해시를 사용합니다.
- 회전 시 기존 토큰을 조건부 UPDATE로 한 번만 사용 처리합니다.
- 사용된 토큰 재제출 또는 회전 경쟁 패배는 토큰 패밀리 탈취 신호로 처리합니다.
- 패밀리 전체를 폐기하며 클라이언트가 다시 로그인하게 합니다.
- 회전으로 패밀리 절대 만료를 연장하지 않습니다.
- 로그아웃은 토큰 존재 여부를 노출하지 않는 멱등 작업입니다.

## 5. 권한과 소유권

- 캐릭터, 재화, 방은 요청 params의 userId가 아니라 JWT의 사용자 ID를 사용합니다.
- 스테이지 실행 완료 시 실행의 userId와 호출자 ID를 비교합니다.
- 다른 사용자 소유 자원에 접근할 수 있는 RPC를 이번 범위에서 제공하지 않습니다.
- 향후 다른 플레이어 방 조회가 추가되면 공개 범위와 비공개 필드를 별도 계약으로 정의합니다.

## 6. 입력 검증

- 전송 계층에서 본문 크기, Content-Type, JSON 깊이, 배치 수를 제한합니다.
- RPC 계층에서 Request Object와 params 타입을 검증합니다.
- 업무 계층에서 열거 값, 수치 범위, 좌표, 중복, 상태 전이를 검증합니다.
- DB에서 외래 키, 유일, 체크 제약으로 마지막 무결성을 보장합니다.
- SQL은 Dapper 매개변수만 사용하고 식별자나 정렬 필드를 입력에서 직접 받지 않습니다.

## 7. 치트와 신뢰 한계

현재 스테이지 완료 검증은 서버 시작 시각과 최소 클리어 시간만 확인합니다. 플레이 결과, 이동 경로, 함정 충돌, 클라이언트 상태를 검증하지 않으므로 강한 치트 방지가 아닙니다.

실서비스 보상을 보호하려면 다음 중 하나가 별도 요구사항으로 필요합니다.

- 서버 권위 시뮬레이션
- 서명된 리플레이와 결정론적 검증
- 이벤트 시퀀스 검증과 이상 탐지
- 보상 위험도별 추가 검증

이 한계를 README나 운영 정책에서 실제 보안 보장처럼 표현하지 않습니다.

## 8. 로깅과 오류

기록 금지:

- Authorization 헤더
- Google ID 토큰
- 액세스·리프레시 토큰
- JWT 서명 키
- 전체 RPC params와 원문 요청 본문
- SQL 매개변수의 민감값
- 외부 제공자 사용자 ID 원문

기록 허용:

- traceId
- RPC 메서드
- 내부 userId
- 오류 코드와 안정적인 오류 key
- 소요 시간
- 토큰 재사용 탐지 이벤트의 familyId 축약 해시

외부 오류 응답에는 예외 메시지, 파일 경로, SQL, 스택 추적을 포함하지 않습니다.

## 9. 설정과 비밀값

- 저장소의 `appsettings.json`에는 안전한 기본값과 비밀이 아닌 제한값만 둡니다.
- 로컬 개발은 .NET User Secrets 또는 환경 변수를 사용합니다.
- 배포는 운영 환경의 비밀 저장소 또는 서비스 환경 변수를 사용합니다.
- 서명 키는 최소 32바이트의 충분한 엔트로피를 가져야 합니다.
- SQLite 파일과 백업의 OS 권한을 서비스 계정으로 제한합니다.

## 10. 개발 기능

- `auth.login.development`는 Development 환경에서만 메서드 Registry에 등록합니다.
- 운영 설정 하나만으로 실수로 활성화되지 않도록 ASP.NET Core Environment와 명시적인 옵션을 함께 확인합니다.
- 개발 사용자 seed와 운영 마이그레이션을 분리합니다.

## 11. 속도 제한과 자원 고갈

- 로그인·토큰 메서드는 IP별 분당 10회 기본 제한을 둡니다.
- 일반 RPC는 사용자 ID 또는 IP별 초당 120회 기본 제한을 둡니다.
- 요청 64 KiB, 배치 50개, JSON 깊이 32를 기본 상한으로 둡니다.
- 각 배치 요소의 오류가 전체 프로세스를 중단시키지 않도록 예외 경계를 둡니다.
- SQLite busy timeout과 제한적 재시도로 잠금 폭주를 완화합니다.

## 12. 보안 테스트 최소 목록

- JWT 발급자, 대상, 만료, 서명 오류
- `sub` 누락·문자열 오류·존재하지 않는 사용자
- Google audience 불일치와 subject 누락
- 리프레시 토큰 원문 미저장 검증
- 리프레시 토큰 동시 회전과 재사용 패밀리 폐기
- 다른 사용자 스테이지 실행 완료 시도
- 음수·오버플로 재화 변경
- SQL injection 형태 문자열 입력
- 로그에 토큰과 Authorization 헤더가 없는지 검증
- Production에서 개발 로그인 미등록 검증
