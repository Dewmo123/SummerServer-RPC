# AI 커밋 메시지 가이드

## 목표

커밋 메시지는 AI가 스테이징된 변경만 분석해 작성합니다. 실제로 수행하지 않은 테스트나 코드에 없는 효과를 주장하지 않습니다.

## 형식

```text
<type>(<scope>): <한국어 제목>

<선택적 본문>

<선택적 footer>
```

### type

| type | 용도 |
|---|---|
| `feat` | 사용자 또는 서버 기능 추가 |
| `fix` | 잘못된 동작 수정 |
| `refactor` | 외부 동작 없는 구조 개선 |
| `test` | 테스트만 변경 |
| `docs` | 문서만 변경 |
| `build` | 패키지, SDK, 빌드 설정 |
| `ci` | CI/CD 워크플로 |
| `chore` | 위 분류에 속하지 않는 유지보수 |

### scope

권장 scope:

```text
rpc
auth
character
currency
stage
room
database
catalog
logging
security
docs
```

## 제목 규칙

- 한국어로 작성합니다.
- 명령형보다 변경 결과가 분명한 서술형을 사용합니다.
- 마침표를 붙이지 않습니다.
- 50자 안팎을 권장합니다.
- `수정`, `변경`, `작업`만으로 끝내지 말고 대상을 구체적으로 씁니다.

좋은 예:

```text
feat(rpc): 알림과 혼합 배치 디스패치 구현
fix(auth): 동시 토큰 회전 시 패밀리 폐기 보장
docs(stage): 완료 보상 트랜잭션 계약 명확화
```

피할 예:

```text
fix: 수정
update files
feat: AI로 코드 작성
```

## 본문 규칙

- 무엇이 바뀌었는지와 필요한 이유를 2~4개 항목으로 설명합니다.
- 파일 목록을 그대로 나열하지 않습니다.
- 테스트를 실행했다면 실제 명령과 결과만 언급합니다.
- 요구사항 ID가 있으면 footer에 `Refs:`로 연결합니다.
- 호환되지 않는 계약 변경은 `BREAKING CHANGE:`를 명시합니다.

## 생성 프롬프트

```text
git diff --cached의 내용만 분석하여 커밋 메시지를 작성하라.

규칙:
- Conventional Commits 형식을 사용한다.
- 제목과 본문은 한국어로 작성한다.
- diff에 없는 변경 효과를 주장하지 않는다.
- 실행 기록이 확인되지 않은 테스트를 통과했다고 쓰지 않는다.
- 관련 문서에 요구사항 ID가 있으면 footer에 Refs로 기록한다.
- 변경이 여러 목적을 섞고 있으면 커밋 분리를 먼저 제안하고 메시지를 만들지 않는다.
- 비밀값처럼 보이는 내용은 메시지에 복사하지 않는다.
- 출력은 커밋 메시지 또는 커밋 분리 제안만 제공한다.
```

## 예시

```text
feat(stage): 스테이지 완료 보상 처리 구현

- 진행 중 실행을 조건부 갱신해 중복 완료 차단
- Gold와 경험치 지급을 동일 트랜잭션으로 처리
- 최소 클리어 시간과 동시 완료 테스트 추가

Refs: FR-STAGE-003
```

```text
docs(architecture): JSON-RPC 모노리스 기준선 작성

- 기능 요구사항과 RPC 메서드 계약 연결
- SQLite 데이터 모델과 Dapper 트랜잭션 경계 정의
- AI 주석 및 커밋 메시지 규칙 추가
```

## 자동화 안전 규칙

- AI는 커밋 메시지를 만들기 전에 `git status --short`와 `git diff --cached`를 확인합니다.
- 스테이징되지 않은 파일을 메시지 근거로 사용하지 않습니다.
- 빌드 또는 테스트 실패 중에는 자동 커밋하지 않습니다.
- `.db`, 로그, 토큰, 키, 사용자 비밀값이 스테이징되면 즉시 중단합니다.
- 자동 push와 자동 배포는 커밋 메시지 생성과 별개의 권한으로 취급합니다.
