# 앱 요구사항

## 1. 문서 정보

- 제품: Summer Project Server
- 기준선: 0.1
- 기준일: 2026-08-19
- 상태: 신규 구현 기준선
- 대상: .NET 10 JSON-RPC 모노리스 서버

## 2. 제품 개요

이 제품은 다른 플레이어와 실시간 연결하지 않아도 성장과 방 구성을 공유할 수 있는 비동기 멀티플레이 게임의 서버입니다. 현재 확인된 범위는 외부 계정 로그인, 세션 유지, 캐릭터 성장, 재화, 정적 스테이지 진행, 개인 방의 맵·함정 배치입니다.

## 3. 목표

- 클라이언트가 하나의 JSON-RPC 엔드포인트로 서버 기능을 호출할 수 있어야 합니다.
- 인증과 게임 기능을 하나의 배포 가능한 서버로 통합해야 합니다.
- SQLite와 Dapper를 사용해 로컬 개발과 단일 인스턴스 운영을 단순화해야 합니다.
- 중복 로그인, 토큰 재사용, 중복 보상, 잘못된 함정 배치로 데이터가 훼손되지 않아야 합니다.
- 요구사항, RPC 계약, 코드, 테스트를 식별자로 추적할 수 있어야 합니다.

## 4. 사용자와 외부 시스템

| 주체 | 책임 |
|---|---|
| 게임 클라이언트 | JSON-RPC 요청 전송, 액세스·리프레시 토큰 보관, 결과 처리 |
| 인증되지 않은 플레이어 | 로그인, 토큰 갱신, 공개 스테이지 조회 |
| 인증된 플레이어 | 캐릭터·재화 조회, 스테이지 진행, 방 구성 관리 |
| Google 인증 서비스 | Google ID 토큰의 서명, 발급자, 대상, 만료 검증 근거 제공 |
| 운영자 | 서버 설정, SQLite 백업, 로그 및 상태 확인 |

## 5. 기능 요구사항

### FR-AUTH-001 Google 로그인

서버는 Google ID 토큰을 허용된 Client ID 목록에 대해 검증해야 합니다.

인수 조건:

- 유효한 토큰의 `subject`로 기존 사용자를 찾습니다.
- 최초 로그인이라면 Google 제공자와 제공자 사용자 ID 조합으로 사용자를 한 번만 생성합니다.
- 동일 계정의 동시 최초 로그인에서도 사용자 행은 하나만 존재해야 합니다.
- 초기 사용자명은 외부 식별자를 그대로 노출하지 않는 결정적 값이어야 합니다.
- 성공 시 사용자 정보, 액세스 토큰, 리프레시 토큰과 각 만료 시각을 반환합니다.
- 토큰 검증 실패 시 `AUTH_INVALID_GOOGLE_TOKEN` 오류를 반환합니다.

RPC: `auth.login.google`

### FR-AUTH-002 개발 로그인

서버는 로컬 개발에서 고정된 개발 사용자로 로그인할 수 있어야 합니다.

인수 조건:

- Development 환경에서만 메서드를 등록합니다.
- 설정된 개발 사용자가 없으면 `AUTH_DEVELOPMENT_USER_NOT_FOUND`를 반환합니다.
- 성공 응답 형식은 Google 로그인과 동일합니다.
- Production과 Staging 환경에서는 메서드가 존재하지 않는 것처럼 처리합니다.

RPC: `auth.login.development`

### FR-AUTH-003 액세스 토큰

서버는 인증 성공 시 서명된 JWT 액세스 토큰을 발급해야 합니다.

인수 조건:

- 토큰은 `sub`, `jti`, `username`, `provider` 클레임을 포함합니다.
- 기본 수명은 60분이며 설정으로 조정할 수 있습니다.
- 발급자, 대상, 수명, 서명 키를 모두 검증합니다.
- 허용 시계 오차 기본값은 30초입니다.
- 인증이 필요한 RPC는 유효하지 않은 토큰에 `AUTH_UNAUTHENTICATED`를 반환합니다.

### FR-AUTH-004 리프레시 토큰 회전

서버는 유효한 리프레시 토큰을 사용할 때 새 토큰으로 회전시켜야 합니다.

인수 조건:

- 원문 토큰 대신 SHA-256 해시만 DB에 저장합니다.
- 리프레시 토큰 기본 수명은 30일입니다.
- 회전된 토큰은 기존 토큰과 같은 절대 만료 시각을 유지합니다.
- 한 토큰은 한 번만 성공적으로 회전할 수 있습니다.
- 사용된 토큰이 다시 제출되면 해당 토큰 패밀리를 모두 폐기합니다.
- 성공 시 새 액세스 토큰과 새 리프레시 토큰을 반환합니다.

RPC: `auth.token.refresh`

### FR-AUTH-005 로그아웃

서버는 제출된 리프레시 토큰이 속한 토큰 패밀리를 폐기해야 합니다.

인수 조건:

- 존재하지 않거나 이미 폐기된 토큰의 로그아웃도 성공으로 처리합니다.
- 응답으로 토큰 존재 여부를 노출하지 않습니다.
- 폐기된 토큰은 이후 갱신에 사용할 수 없습니다.

RPC: `auth.logout`

### FR-CHAR-001 내 캐릭터 조회

인증된 플레이어는 자신의 캐릭터 성장 상태를 조회할 수 있어야 합니다.

인수 조건:

- 캐릭터가 없으면 레벨 1, 경험치 0으로 한 번만 생성합니다.
- 응답은 현재 레벨, 현재 레벨 내 경험치, 다음 레벨 요구 경험치를 포함합니다.
- 다음 레벨 요구 경험치는 `100 × 현재 레벨`입니다.
- 존재하지 않는 사용자에게 캐릭터를 생성하지 않습니다.

RPC: `character.getMine`

### FR-CHAR-002 경험치 지급

서버 내부 업무 흐름은 양수 경험치를 캐릭터에 지급할 수 있어야 합니다.

인수 조건:

- 경험치가 요구량 이상이면 남은 경험치를 보존하며 여러 레벨을 연속 상승시킵니다.
- 0 이하 경험치 지급은 거부합니다.
- 정수 범위를 넘는 결과는 전체 트랜잭션을 실패시킵니다.
- 스테이지 보상과 동일한 트랜잭션에서 수행할 수 있어야 합니다.

### FR-CURRENCY-001 특정 재화 조회

인증된 플레이어는 특정 재화의 잔액을 조회할 수 있어야 합니다.

인수 조건:

- 지원 재화는 Gold(1), Gem(2), StageTicket(3), EventToken(4)입니다.
- 사용자에게 해당 재화 행이 없으면 잔액 0으로 한 번만 생성합니다.
- 정의되지 않은 재화 값은 `CURRENCY_INVALID_TYPE` 오류입니다.
- 응답은 재화 종류와 잔액을 포함합니다.

RPC: `currency.getMine`

### FR-CURRENCY-002 전체 재화 조회

인증된 플레이어는 지원되는 모든 재화 잔액을 한 번에 조회할 수 있어야 합니다.

인수 조건:

- 누락된 재화 행은 잔액 0으로 생성합니다.
- 응답에는 모든 지원 재화가 한 번씩 포함됩니다.

RPC: `currency.listMine`

### FR-CURRENCY-003 재화 변경

서버 내부 업무 흐름은 재화를 원자적으로 증가하거나 차감할 수 있어야 합니다.

인수 조건:

- 변경량은 양수여야 합니다.
- 잔액은 음수가 될 수 없습니다.
- 증가 결과가 64비트 정수 범위를 넘을 수 없습니다.
- 잔액 확인과 갱신 사이의 경쟁 조건으로 중복 차감이나 초과 지급이 발생하지 않아야 합니다.

### FR-STAGE-001 정적 스테이지 조회

인증 여부와 관계없이 정적 스테이지 데이터를 조회할 수 있어야 합니다.

인수 조건:

- 응답은 스테이지 ID, 크기, 타일, 함정, 최소 클리어 시간, 경험치·Gold 보상을 포함합니다.
- 존재하지 않는 스테이지는 `STAGE_NOT_FOUND` 오류입니다.
- 정적 카탈로그는 서버 시작 시 검증하고 메모리에 적재합니다.

RPC: `stage.get`

### FR-STAGE-002 스테이지 입장

인증된 플레이어는 존재하는 스테이지의 새로운 실행을 시작할 수 있어야 합니다.

인수 조건:

- 사용자와 스테이지가 모두 존재해야 합니다.
- 같은 사용자의 기존 진행 중 실행은 `Abandoned` 상태와 완료 시각으로 변경합니다.
- 새로운 실행은 `InProgress` 상태와 서버 UTC 시작 시각을 가집니다.
- 기존 실행 정리와 새 실행 생성은 하나의 트랜잭션입니다.
- 성공 시 실행 ID와 스테이지 데이터를 반환합니다.

RPC: `stage.enter`

### FR-STAGE-003 스테이지 완료와 보상

인증된 플레이어는 자신이 시작한 진행 중 실행을 한 번만 완료할 수 있어야 합니다.

인수 조건:

- 실행이 존재하고 요청 사용자 소유여야 합니다.
- 상태가 `InProgress`여야 합니다.
- 서버 시작 시각부터 스테이지 최소 클리어 시간이 경과해야 합니다.
- 동시 완료 요청 중 하나만 완료 상태를 선점할 수 있습니다.
- 완료 기록, Gold 지급, 경험치 지급은 하나의 트랜잭션으로 커밋합니다.
- 응답은 스테이지 ID, 획득 경험치, 획득 재화, 전체 재화, 갱신된 캐릭터를 포함합니다.
- 보상 지급 일부가 실패하면 실행 상태와 모든 보상 변경을 롤백합니다.

RPC: `stage.complete`

### FR-ROOM-001 내 방 저장

인증된 플레이어는 자신의 방에 사용할 맵과 함정 배치를 생성하거나 교체할 수 있어야 합니다.

인수 조건:

- 요청 본문은 HTTP 계층에서 최대 64 KiB입니다.
- 맵 ID는 정적 카탈로그에 존재해야 합니다.
- 함정은 최대 100개입니다.
- 함정 종류는 서버가 지원하는 열거 값이어야 합니다. 현재 확인된 종류는 SawTrap입니다.
- 좌표는 `0 ≤ x < width`, `0 ≤ y < height`, `z = 0`이어야 합니다.
- 같은 좌표에 둘 이상의 함정을 배치할 수 없습니다.
- quaternion 크기의 제곱은 0.98 이상 1.02 이하여야 합니다.
- 사용자별 방은 하나만 존재하며 다시 저장하면 전체 구성을 교체합니다.

RPC: `room.upsertMine`

### FR-ROOM-002 내 방 조회

인증된 플레이어는 자신의 저장된 방 구성을 조회할 수 있어야 합니다.

인수 조건:

- 응답은 사용자 ID, 맵 데이터, 함정 배열을 포함합니다.
- 저장된 방이 없으면 `ROOM_NOT_FOUND` 오류입니다.
- 저장된 맵 ID가 카탈로그에 없으면 데이터 무결성 오류 `ROOM_MAP_INVALID`를 반환하고 운영 로그에 기록합니다.

RPC: `room.getMine`

### FR-SYSTEM-001 상태 확인

운영 환경은 JSON-RPC와 분리된 `GET /health` 엔드포인트를 제공해야 합니다.

인수 조건:

- 프로세스 생존 여부와 SQLite 연결·간단 쿼리 가능 여부를 확인합니다.
- 상태 응답에 비밀값, 경로 전체, 예외 스택을 포함하지 않습니다.

## 6. 업무 규칙

| ID | 규칙 |
|---|---|
| BR-AUTH-001 | 외부 로그인 계정은 `provider + providerUserId` 조합으로 유일합니다. |
| BR-AUTH-002 | 리프레시 토큰 패밀리의 절대 만료는 회전으로 연장되지 않습니다. |
| BR-AUTH-003 | 사용된 리프레시 토큰 재사용은 탈취 가능성으로 보고 패밀리 전체를 폐기합니다. |
| BR-CHAR-001 | 캐릭터는 사용자당 하나입니다. |
| BR-CHAR-002 | 레벨은 1 이상, 경험치는 0 이상입니다. |
| BR-CURRENCY-001 | 재화 잔액은 0 이상입니다. |
| BR-CURRENCY-002 | 사용자와 재화 종류 조합은 유일합니다. |
| BR-STAGE-001 | 사용자에게 의미 있는 진행 중 스테이지 실행은 최대 하나입니다. |
| BR-STAGE-002 | 완료된 실행에는 보상을 다시 지급하지 않습니다. |
| BR-ROOM-001 | 사용자당 방은 하나입니다. |
| BR-ROOM-002 | 방과 스테이지의 맵·함정 정의는 정적 카탈로그를 기준으로 검증합니다. |

## 7. 비기능 요구사항

| ID | 요구사항 |
|---|---|
| NFR-PROTOCOL-001 | 모든 RPC는 JSON-RPC 2.0 스펙의 단일, 알림, 배치 요청을 처리합니다. |
| NFR-PROTOCOL-002 | 메서드와 이름 기반 파라미터는 대소문자를 구분합니다. |
| NFR-SECURITY-001 | 비밀값과 토큰 원문은 코드, 설정 파일, 로그, 오류 응답에 남기지 않습니다. |
| NFR-SECURITY-002 | 모든 SQL은 Dapper 매개변수로 실행합니다. |
| NFR-RELIABILITY-001 | 중복 토큰 회전과 중복 스테이지 완료는 조건부 갱신으로 한 요청만 성공시킵니다. |
| NFR-RELIABILITY-002 | DB 마이그레이션은 순서와 체크섬을 기록하고 반복 실행에 안전해야 합니다. |
| NFR-OBSERVABILITY-001 | ZLogger 구조화 로그에 요청 ID, RPC 메서드, 소요 시간, 결과 오류 코드를 남깁니다. |
| NFR-OBSERVABILITY-002 | 인증 토큰과 전체 params는 기본 로그 대상에서 제외합니다. |
| NFR-MAINTAINABILITY-001 | 프로덕션 프로젝트는 하나이며 기능별 폴더 경계를 유지합니다. |
| NFR-MAINTAINABILITY-002 | 공개 계약 타입은 네이밍 규칙과 한국어 주석 지침을 따릅니다. |
| NFR-TEST-001 | 프로토콜, 업무 규칙, SQLite 통합, 인증 보안 테스트를 자동화합니다. |
| NFR-PERFORMANCE-001 | 기본 최대 배치 크기와 요청 크기를 설정으로 제한합니다. |
| NFR-COMPAT-001 | 모든 시간은 UTC로 처리하고 외부 응답은 ISO 8601 형식으로 직렬화합니다. |

## 8. 범위 밖

다음 기능은 현재 소스에서 구현 또는 계약을 확인할 수 없어 이번 기준선에서 제외합니다.

- 다른 플레이어의 방 검색과 실제 약탈 결과 처리
- 매칭, 랭킹, 리더보드
- 방어 결과와 오프라인 보상
- 캐릭터 장비, 스킬, 인벤토리
- 함정 구매, 강화, 소유권 검증
- 결제와 상점
- 운영자용 관리 API
- 클라이언트 플레이 결과의 치트 방지 또는 리플레이 검증
- 다중 서버 인스턴스와 분산 SQLite 쓰기

## 9. 미결정 사항

- 기존 운영 DB 데이터를 새 SQLite DB로 실제 이전할지, 개발 데이터를 새로 시작할지 결정이 필요합니다.
- 최초 배포에서 Google 로그인만 지원할지 Guest 로그인을 추가할지 결정이 필요합니다.
- 실제 약탈 기능의 권한·보상·검증 계약은 별도 제품 요구사항이 필요합니다.
- 목표 운영 환경의 RPO, RTO, 최대 동시 사용자와 최대 DB 크기를 확정해야 합니다.
- 스테이지 타일 배열 길이가 `width × height`와 일치해야 하는지 카탈로그 검증 규칙으로 확정해야 합니다.
- 현재 추적된 저장소에 원본 Map1/Stage1 JSON 전체가 없어 타일 내용과 Stage1 함정의 최종 위치·회전은 콘텐츠 기준 확인이 필요합니다.
